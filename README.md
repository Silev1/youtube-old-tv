# tvyt — YouTube для старых Samsung TV (Orsay, 2011–2014)

Локальный сервер на Debian, который возвращает YouTube на старый телевизор Samsung.
Телевизор — это плеер (встроенный браузер), телефон — пульт.

```
┌──────────────┐   HTTP    ┌───────────────────┐   yt-dlp   ┌──────────┐
│  Телефон     │ ────────► │  Мини-сервер      │ ─────────► │ YouTube  │
│  (пульт,     │  /api/*   │  Debian + Python  │  ffmpeg    │          │
│   поиск)     │ ◄──────── │  :80              │ ◄───────── │          │
└──────────────┘           └───────────────────┘            └──────────┘
                                    │  /stream/<id>.mp4
                                    ▼
                           ┌──────────────────┐
                           │ Samsung TV       │
                           │ браузер+<video>  │
                           └──────────────────┘
```

## Зачем

Samsung UE32ES5507 (2012, платформа Orsay) больше не открывает YouTube: старый
браузер не тянет современный сайт, а приложение YouTube в Smart Hub отключено.
Покупать новый телевизор ради этого не нужно — телевизор умеет играть
H.264/AAC из обычного MP4, а скачать и перекодировать может дешёвый ноутбук.

## Что умеет

- Поиск по YouTube с телефона (`yt-dlp`, без API-ключа и без капчи).
- Скачивание в **480p H.264 Main / AAC-LC** — 854×480, ~660 кбит/с, ~17 МБ на 3 минуты.
  Меньше места на диске и гарантированно тянет декодер 2012 года.
- Отдача файла по HTTP с поддержкой `Range` (перемотка, 206 Partial Content).
- Очередь воспроизведения, автопереход к следующему видео.
- Автоматическая очистка кэша (лимит 12 ГБ).
- Автозапуск через systemd, статический IP, блокировка сна.

## Требования

| | |
|---|---|
| Сервер | любой x86/ARM ноутбук или мини-ПК, Debian 12/13, ~100 МБ на видео |
| Пакеты | `python3` (>= 3.9), `ffmpeg`, `yt-dlp` |
| Сеть | сервер и телевизор в одной локальной сети |
| Телевизор | Samsung Orsay (2011–2014) со встроенным браузером |

Ни Flask, ни pip не нужны — сервер на чистой стандартной библиотеке Python.

## Установка

### 1. Пакеты

```sh
apt-get update
apt-get install -y ffmpeg
curl -sL -o /usr/local/bin/yt-dlp \
  https://github.com/yt-dlp/yt-dlp/releases/latest/download/yt-dlp_linux
chmod +x /usr/local/bin/yt-dlp
```

`yt-dlp` нужен именно отдельным бинарником: из apt он отстаёт на месяцы и
ломается о защиту YouTube.

### 2. Приложение

```sh
mkdir -p /opt/tvyt/cache
cp app.py /opt/tvyt/app.py
cp tvyt.service /etc/systemd/system/tvyt.service
systemctl daemon-reload
systemctl enable --now tvyt
```

Всё это вместе с таймером обновления делает `deploy.sh`:

```sh
sh deploy.sh
```

### 2.1. Автообновление yt-dlp

YouTube регулярно ломает старые версии `yt-dlp` — через месяц-два скачивание
перестаёт работать с ошибкой вида «Sign in to confirm you're not a bot».
Поэтому раз в неделю таймер обновляет бинарник:

```sh
cp update-ytdlp.sh /usr/local/bin/update-ytdlp.sh
chmod +x /usr/local/bin/update-ytdlp.sh
cp tvyt-update.service tvyt-update.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now tvyt-update.timer
```

Проверить и запустить вручную:

```sh
systemctl list-timers tvyt-update      # когда следующий раз
systemctl start tvyt-update.service    # обновить сейчас
journalctl -u tvyt-update -n 20        # что было в прошлый раз
```

Скрипт скачивает релиз во временный файл, проверяет что он запускается и
возвращает версию, и только потом подменяет бинарник. Если GitHub недоступен
или файл битый — остаётся прежняя рабочая версия, сервис не ломается.
Перезапуск `tvyt` не требуется: `yt-dlp` вызывается как подпроцесс.

Расписание — понедельник 04:30 плюс случайный разброс до часа.

### 3. Статический IP

Телевизор запоминает адрес, поэтому сервер должен всегда получать один и тот же.
Для `dhcpcd` (`/etc/dhcpcd.conf`):

```
interface enp3s0
static ip_address=192.168.0.50/24
static routers=192.168.0.1
static domain_name_servers=192.168.0.1
```

В Debian 13 юнит `dhcpcd.service` идёт с ошибкой — в секции `[install]`
написано строчными буквами, из-за чего автозапуск не включается и после
перезагрузки сеть не поднимается. Чинится скриптом `netfix.sh`.

### 4. Запретить сон

```sh
systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
```

## Использование

1. На телевизоре: Smart Hub → «Веб-браузер» → `http://192.168.0.50/tv`
2. На телефоне: `http://192.168.0.50` → запрос → «▶ Играть».

Пультом на телевизоре: **OK** — пауза/воспроизведение, **←/→** — 10 секунд.

## Страницы

| URL | Назначение |
|---|---|
| `/` | пульт для телефона: поиск, очередь, пауза |
| `/tv` | плеер для телевизора (минимальная страница) |
| `/tv2` | альтернатива: навигация на голый MP4 (родной плеер) |
| `/tv3` | отладочная версия плеера с подробной телеметрией |

`/tv3` присылает в журнал сервера всё, что происходит с `<video>`: события,
`readyState`, `videoWidth`, геометрию элемента. Именно этим нашлась причина
чёрного экрана — см. ниже.

## API

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/state` | состояние: `rev`, `current`, `queue`, `cmd`, `report` |
| GET | `/api/search?q=…` | поиск, возвращает `[{id,title,dur,len}]` |
| GET | `/api/thumb?id=…` | превью (проксируется с i.ytimg.com) |
| POST | `/api/play` | `{id,title,next}` — играть сейчас или в очередь |
| POST | `/api/cmd` | `{action,value}` — `pause`, `next`, `prev`, `seek`, `stop` |
| POST | `/api/report` | телеметрия от телевизора: `{pos,dur,paused,ended}` |
| GET | `/stream/<id>.mp4` | сам файл, `Range`/206 |

Состояние живёт в памяти процесса; ссылки на файлы — в `/opt/tvyt/cache`.

## Грабли Orsay (главное)

Этот раздел — концентрат того, что пришлось выяснить на живом UE32ES5507
(браузер `Mozilla/5.0 (SMART-TV; X11; Linux i686) AppleWebKit/534.7 … Version/5.0 Safari/534.7`).

**1. `canPlayType` врёт оптимистично, но играет нормально.**
`video/mp4; codecs="avc1.4D401E,mp4a.40.2"` → `"probably"`. 480p H.264 Main@3.0
и AAC-LC воспроизводятся. 720p тоже играет, но на 480p меньше нагрузка и трафик.

**2. `<source>` внутри `<video>` не работает.**
С `<video><source src="…"></video>` телевизор скачивает файл целиком и **не
передаёт его декодеру** — чёрный экран без ошибки. Работает только присвоение
`video.src = '…'` напрямую. Проверяется по логу: при рабочем варианте следом
появляется запрос с `User-Agent: Lavf52.104.0` (это libavformat внутри
телевизора), при сломанном — его нет.

**3. Чёрный экран при играющем видео — это фон страницы.**
Видео декодируется (`currentTime` растёт, `videoWidth` = 854), но не видно.
Причина: телевизор рисует видео в отдельной плоскости, а непрозрачный фон
`html,body` её перекрывает. Лечится `background: transparent` и минимальной
вёрсткой — без абсолютного позиционирования, оверлеев поверх видео и градиентов.

**4. Оверлей поверх видео не убирается по событию.**
Событие `playing` приходит, но страховка нужна: раз в 0.4 с проверять
`currentTime > 0` и прятать оверлей. Иначе «Готово» висит поверх фильма.

**5. Навигация на голый MP4 не открывает родной плеер.**
`location.href = '/stream/x.mp4'` — телевизор скачивает файл и пишет
«не удалось запустить». Query-строка (`?a=123`) усугубляет. Единственный
рабочий путь — `<video src>` внутри страницы.

**6. Faststart обязателен.**
`moov` должен быть в начале файла, иначе старый libavformat ждёт загрузки
хвоста. В `app.py` это делает `ensure_faststart()` (`ffmpeg -c copy -movflags
+faststart`), у готовых файлов рядом лежит маркер `.fs`.

**7. Браузер кэширует страницу агрессивно.**
После обновления `app.py` нужно вручную перезагрузить страницу на телевизоре,
иначе он крутит старый JS.

**8. Мусор в консоли — не ваш.**
`ReferenceError: Can't find variable: MostVisitedUI` сыплется из самого
браузера (Smart Hub), к странице отношения не имеет. Отфильтровано в `onerror`.

## Включение сервера по сети (Wake-on-LAN)

Сервер — ноутбук, и его можно включать удалённо, не подходя к нему.

Настройка уже сделана юнитом `tvyt-wol.service` (скрипт `wol-enable.sh`):

```sh
cp wol-enable.sh /usr/local/bin/wol-enable.sh
chmod +x /usr/local/bin/wol-enable.sh
cp tvyt-wol.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now tvyt-wol
```

Что он делает при каждой загрузке (после ребута настройки сбрасываются):

1. `ethtool -s enp3s0 wol g` — карта принимает magic packet;
2. `echo enabled > .../power/wakeup` — разрешает пробуждение на уровне PCI;
3. включает `PXSX` в `/proc/acpi/wakeup` — пробуждение из **S5** (полное выключение).

Проверка:

```sh
ethtool enp3s0 | grep 'Wake-on'      # должно быть Wake-on: g
grep PXSX /proc/acpi/wakeup          # должно быть *enabled
```

### Как включить

С Windows (скрипт `wake-tvyt.ps1`, MAC уже прописан):

```powershell
powershell -ExecutionPolicy Bypass -File wake-tvyt.ps1
```

или двойным щелчком по `wake-tvyt.cmd`. Скрипт отправляет пакет на
`192.168.0.255:9` (и дублирует на порт 7) и ждёт, пока сервер ответит на пинг.

С телефона: любое приложение «Wake On Lan», MAC `98:4B:E1:95:38:CF`,
адрес `192.168.0.255`, порт 9.

### Что важно знать

- **Кабель, не Wi-Fi.** Пробуждение работает только по Ethernet: Wi-Fi-карта
  в выключенном ноутбуке не питается. У сервера `wlp2s0b1` не используется.
- **Wake-on-LAN не использует IP.** Пакет идёт на MAC-адрес широковещательно,
  поэтому статический IP нужен только чтобы потом попасть на сервер, а не для
  самого пробуждения.
- **BIOS.** Если в BIOS ноутбука выключен «Wake on LAN» / включён «ErP» (полное
  отключение питания в выключенном состоянии), пробуждение не сработает —
  из операционной системы это не лечится.
- **Только своя локальная сеть.** Broadcast за пределы роутера не выходит.
  Для пробуждения извне нужен port forwarding и устройство, которое всегда
  включено (роутер с поддержкой WoL или Raspberry Pi).
- После `shutdown` индикатор на сетевом порту обычно продолжает гореть —
  это признак того, что карта в режиме ожидания magic packet.

## Отладка

```sh
journalctl -u tvyt -f                 # сам сервер
journalctl -u tvyt-update -n 50       # обновления yt-dlp
```
Полезное в логе:

```
GET /stream/<id>.mp4 … ua=Lavf52.104.0 rng=bytes=0-   # декодер забрал файл — хорошо
TVLOG {"kind":"hb","t":41.2,"vw":854,"rs":4}          # играет, кадры идут
TVLOG {"kind":"vid","e":"error","er":4}               # декодер отказался
```

Если `hb` идёт, а экран чёрный — проблема в вёрстке, а не в файле.

## Ограничения

- Управление с телефона — только пауза и переключение треков; перемотка
  пультом телевизора (жесты браузера на Orsay ненадёжны).
- Кэш не переживает перезапуск сервиса как состояние, но файлы остаются.
- Один телевизор на инстанс: состояние одно на процесс.
- Скачивание идёт в реальном времени, перед стартом 5–20 секунд ожидания.
